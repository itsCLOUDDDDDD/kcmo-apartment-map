# Sheet to website: current mapping

## Ownership and delivery

The live Google Sheet owns property facts. A fresh XLSX export supplies the multiple tabs used by the exporter. CSV alone cannot carry this workbook's support sheets and formulas. The private sheet URL must be supplied to the chat separately; repository access does not grant sheet access.

Current path: live sheet → explicit XLSX snapshot → workbook exporter → local `map-data.js` preview → review/tests → copy reviewed output into the publishing repository → commit/push → successful GitHub Pages deployment.

The site reads `window.KCMO_MAP_DATA`. It does not fetch or edit the live sheet. The website root's JS/CSS/HTML controls display; `src/map-runtime/` contains the editable renderer. The `mapcn/` folder contains its compiled public runtime. Scene event/media data is separately supplied through `scene-data.js` and associated assets, not generated by the apartment workbook exporter.

## Repeated data and known gaps

- Candidate Property ID was in BI, but the current exporter still matches Map Details by **name**. Coordinates added only to candidate helper columns do not reach it; it reads Map Details coordinates.
- Candidate city/state was AH. Current generated external links in the exporter hardcode Kansas City, MO. Inspect scope before exporting other cities.
- Candidates AW/AX/AY and AK are live-sheet views, not the current exporter's route inputs. Website route summaries are recalculated from Map Routes and Map Places categories.
- The live sheet's new cluster membership in Scene & Anchors I is not read by the exporter. Changing it does not change the site's core venue selection.
- The newer Standard agency/status, Utility status, Fee status, topic-specific checked dates and review fields are not yet consumed by the exporter.
- Map Details may take priority over candidate values. Do not replace unique qualifications with lookups before preserving them.
- Some site photo/filter enhancements use existing `property-media.js` and `priority-amenities.js`; inspect those overrides before claiming a spreadsheet field is the sole source.
- Incomplete property costs and a complete fit result must not be treated as equivalent. The spreadsheet and payment-standard.js need explicit parity checks.

## Current unit parser

The exporter recognizes lines shaped like this synthetic example:

```text
#203 | 1BR | 750 sq ft | $1,000/mo | Available October 1 | Source: https://example.com/unit/203
```

This illustrates the **existing parser**, not a final redesigned entry format. It supports only a narrow grammar and preserves unmatched prose in unitOptions. A source/availability phrase is not necessarily a verified current quote. Unit photos require unambiguous unit attribution; a shared gallery must not become an exact-unit photo. Retain each unit's rent, size, availability, checked date and source together when improving this flow.

## Daily manual inputs versus intended automation

The user enters confirmed identity/address, unit facts, amenities, links and source evidence. A reasonable calculation can derive totals, standard comparisons, search links and supported route summaries. A formula cannot establish unknown fees, verify amenities from an unrelated photo, or observe a browser's redirected Maps URL.

The target interface puts everyday fields first and groups/hides calculation and evidence support. Detailed history remains available without forcing oversized rows. Stable IDs should be created automatically and kept immutable. The website should consume validated records with source scope, not independently reinterpret ambiguous notes.
